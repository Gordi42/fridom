# Nonhydrostatic & shallow-water: NEW (framework2) vs OLD (framework)

A like-for-like **performance** comparison of the new framework2 model
stack (`fridom.nonhydro2`, `fridom.shallowwater2`) against the shipped
old stack (`fridom.nonhydro`, `fridom.shallowwater`), at matched
configurations, on three metrics: steady-state per-step wall time,
one-time compile cost, and (new model only) static temp device memory.

Generated by `benchmarks/_bench_new_vs_old.py` (a throwaway harness in
this worktree). Both stacks are imported from the same editable install
(`/home/silvano/Projects/fridom/src`), so they run in one process at
identical precision.

---

## 1. Methodology

### Environment
- **Backend:** XLA `cpu` (single process), `jax` 0.10.2.
- **Precision:** float64 — `fridom` enables x64 on import, so both
  stacks run identical dtype (`jax.config.jax_enable_x64 == True`,
  `dtype_real() == numpy.float64`).
- **Stepper:** `AdamBashforth(order=3)` on **both** stacks (the new
  cutover default and the old default), same numeric `dt`.

### Two execution models (the honest caveat)
The two frameworks are architecturally different, and that difference
is exactly what the headline number captures — it is a real, intended
win, not a measurement artifact:

- **OLD** = a Python time loop. `model.step()` dispatches per-module
  jitted `update`s and pays a **host round-trip every step** (the AB
  stepper and the NaN/panic bookkeeping read to host). Per-step cost
  therefore carries fixed Python + dispatch + host-sync overhead on top
  of the device kernels.
- **NEW** = one jitted `lax.scan`. `model.advance(N)` runs all `N`
  steps inside a **single compiled program** (one host round-trip for
  the whole chunk), compiled once and cached. The new model's advantage
  includes eliminating the per-step host round-trip.

A second, smaller asymmetry that *disfavours* the new model (so the new
numbers are, if anything, conservative): the new chunk body runs an
`isfinite` NaN-seam reduction **every step** (S5), whereas the old
`NaNChecker` only checks every 100 steps.

### Matched configuration
Periodic grids on both sides (the new models are periodic-only; the old
`cartesian.Grid` defaults to periodic in every direction, so this is a
genuine match). Same shape, same numeric `dt`, same physics constants,
same stepper.

| | nonhydro | shallowwater |
|---|---|---|
| grid | `n³`, periodic x/y/z | `n²`, periodic x/y |
| domain | 10000 × 10000 × 100 m | 1 × 1 |
| `dt` | 20 s | `2/n` |
| Coriolis | f-plane, `f0 = 1e-4` | f-plane, `f0 = 1.0` |
| stratification / `csqr` | `N² = (50·f0)² = 2.5e-5` | `csqr = 0.01` |
| advection | Centered (on) / disabled (off) | Sadourny nonlinear (on) |
| sizes `n` | 16, 24, 32 | 128, 256, 512 |

Both nonhydro stacks run a **spectral pressure projection** every step
(old: `RFFTPressureSolver`; new: `SpectralPressureSolver`) plus the
Coriolis + buoyancy linear tendency, so the per-step work is
well-matched. For the linear case, advection is disabled on both sides
(`mset.tendencies.advection.disable()` / `advection=False`).

### Timing procedure
- **jax is async** — every timed region ends with
  `jax.block_until_ready` on the returned carry/field leaves before the
  timer stops.
- **Warmup.** OLD: the first 5 `step()`s are timed separately and
  discarded from steady state (the AB order-ramp recompiles over the
  first ~3–4 steps). NEW: the first `advance(K)` compiles the chunk and
  is discarded.
- **Per-step (steady state).** `K = 50` steps per rep, **7 reps**,
  **median** per-step reported. OLD: a Python loop of `K` `step()`s,
  block after the batch, divide by `K`. NEW: `model._chunk_size = K` so
  `advance(K)` is a single compiled `lax.scan` of length `K`, block,
  divide by `K`.
- Each rep is **reseeded to a fixed small initial state** on both
  sides, so every batch does identical, finite work. (The shipped
  shallow-water `Jet` IC is nonlinearly unstable — NaN within ~20–30
  steps at every size — so it is replaced by a matched small Gaussian
  pressure bump. Per-step wall time on dense XLA CPU kernels is
  value-independent, so this changes nothing about the timing; it only
  keeps the run finite and the logs clean.)
- **Compile.** NEW: read directly from the model's own AOT compile log
  (`_CHUNK_COMPILE_LOG`: `lower().compile()` seconds for the length-`K`
  chunk). OLD: "warmup-compile" = (summed wall of the first 5 steps) −
  (5 × steady per-step) — the extra one-time cost the user pays before
  steady state, dominated by the AB order-ramp recompiles.
- **Memory.** NEW: the compiled chunk executable's
  `.memory_analysis().temp_size_in_bytes` (static temp/scratch). OLD:
  per-step jit makes this unobtainable, and the CPU backend does not
  report `peak_bytes_in_use` (`device.memory_stats()` returns nothing),
  so old-side peak memory is **not obtainable** — not faked.

Raw numbers below are medians of 7 reps; they are single-run and carry
normal timing jitter (a few %), largest at the small sizes where the
per-step time is sub-millisecond.

## 3. Interpretation

**The new model wins clearly when the per-step kernel is cheap, and
converges to parity when the kernel is expensive.** This is the
signature of eliminating a *fixed* per-step overhead (host round-trip +
Python dispatch, ~1 ms/step here):

- At the smallest sizes the fixed overhead dominates, so removing it is
  a **2.5× win** (nonhydro n = 16, both advection on and off) and a
  **1.4× win** (shallow-water n = 128).
- As `n` grows the device kernels dominate the wall time and the fixed
  overhead becomes a small fraction of it, so the speedup decays toward
  1× (nonhydro n = 32: 1.04× on / 0.97× off; shallow-water n = 512:
  0.91×). Both frameworks compile essentially the same numerics for the
  inner kernels, so at large `n` they *should* converge — and they do.
- At the largest sizes the new model is at or just below parity
  (0.91–0.97×). Two plausible contributors, both real costs of the new
  architecture rather than measurement error: the per-step `isfinite`
  NaN-seam reduction the new chunk runs every step (vs every 100 steps
  old), and differences between the two pressure-solver implementations.
  The gap is within a few percent and within run-to-run jitter.

**Compile / first-run cost is comparable, and modestly cheaper for the
new model.** New chunk compile is 0.6–1.3 s; old warmup-compile is
0.7–1.7 s. The new model pays this **once** for the whole run (one
cached executable for a given chunk length), whereas the old model's
warmup-compile is the AB order-ramp recompiling over the first few
steps of every fresh start. Neither is a large absolute number at these
CPU sizes.

**Memory looks comparable and sane.** New static temp scales linearly
with point count (nonhydro adv-on: ~33 bytes/point; shallow-water:
~140 bytes/point, reflecting the C-grid + Sadourny scratch), and the
linear (advection-off) nonhydro model uses roughly half the temp of the
advective one (0.49 vs 1.09 MB at n = 16) — advection scratch removed,
as expected. A direct old-vs-new memory comparison is not possible on
CPU because the old per-step-jit path exposes no compiled executable and
the CPU backend reports no device peak; this is stated, not estimated.

### Caveats / residual mismatches
- **Architecture is the comparison, not a confound.** old = Python loop
  with a per-step host round-trip; new = single jitted chunked scan.
  The new model's advantage *is* that architectural change.
- **Pressure solver differs** between the nonhydro stacks (RFFTN vs a
  framework2 spectral solver). Both project every step, but the inner
  algorithm is not bit-identical — a possible small bias at large `n`.
- **Shallow-water IC swapped** from the unstable shipped `Jet` to a
  matched small Gaussian pressure bump (both sides), purely to keep the
  run finite; timing is value-independent on dense CPU kernels.
- **NaN-checking cadence differs** (new: every step; old: every 100),
  slightly favouring the old model — so the new per-step numbers are
  conservative.
- Numbers are **CPU, single-process, single-run medians** (7 reps).
  Sub-millisecond sizes carry the most jitter. On GPU the fixed-overhead
  elimination would matter over a larger size range (device dispatch and
  host round-trips are relatively more expensive there), so these CPU
  speedups are a lower bound on the architectural benefit for larger,
  accelerator-bound runs.
